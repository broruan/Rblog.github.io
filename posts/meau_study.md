本文整理本工程菜单开发过程中遇到的问题。重点不是只记住某一行怎么改，而是理解菜单树、光标状态、按键事件和数据显示之间的关系。

相关代码：

- [`usr/Src/myfirstmeau.c`](usr/Src/myfirstmeau.c)：菜单初始化、显示和操作
- [`usr/Src/meau.c`](usr/Src/meau.c)：菜单节点创建
- [`usr/Src/main.c`](usr/Src/main.c)：主循环和按键映射
- [`libraries/zf_device/zf_device_key.c`](libraries/zf_device/zf_device_key.c)：按键扫描

## 1. 先建立菜单的整体模型

菜单本质上是一棵树，每个 `Meau_Item` 节点保存：

```c
struct Meau_Item *father;     // 父节点
struct Meau_Item *first_son;  // 第一个子节点
struct Meau_Item *last_bro;   // 上一个兄弟节点
struct Meau_Item *next_bro;   // 下一个兄弟节点
```

当前工程中的结构大致是：

```text
head
|-- s1: Meau1
|-- s2: Meau2
|-- s4: Meau2
`-- s5: Meau2
    `-- s3: aa
```

全局指针 `key` 表示当前光标选中的节点。因此，移动光标、进入菜单和退出菜单，本质上都是修改 `key`：

```c
key = key->next_bro;  // 向下
key = key->last_bro;  // 向上
key = key->first_son; // 进入
key = key->father;    // 返回
```

分析菜单问题时，首先要问：当前 `key` 到底指向哪个节点？

## 2. 为什么进入子菜单后会空指针崩溃

显示当前菜单时，应该遍历“当前父节点”的子项数量：

```c
Meau_Item *h = key->father;
Meau_Item *s = h->first_son;

for(int i = 0; i < h->sons; ++i)
{
    // 显示 s
    s = s->next_bro;
}
```

早期代码使用的是：

```c
for(int i = 0; i < head.sons; ++i)
```

根菜单有 4 项，但 `s5` 下面只有 `aa` 这 1 项。进入 `aa` 所在子菜单后，如果仍循环 4 次：

```text
第 1 次：s == &s3，正常
第 2 次：s == NULL
第 2 次访问 s->name：空指针，可能触发 HardFault
```

结论：遍历哪一级菜单，就必须使用那一级节点的 `sons`，不能固定使用 `head.sons`。当前源码已经改为 `h->sons`。

## 3. 为什么光标可能越界

兄弟链表的首尾指针是 `NULL`：

```c
// 最后一项
key->next_bro == NULL

// 第一项
key->last_bro == NULL
```

如果直接赋值：

```c
key = key->next_bro;
```

光标在最后一项时就会变成 `NULL`。下一轮再执行 `key->father` 会崩溃。

正确做法是先检查边界：

```c
if(key->next_bro != NULL)
{
    key = key->next_bro;
}
```

向上移动同理。当前源码已经增加了首尾检查。

## 4. `KEY_MAX_SHOCK_PERIOD / scanner_period` 是什么意思

这条表达式用于把“消抖时间”换算成“需要连续扫描多少次”：

```c
需要扫描次数 = 消抖时间 / 每次扫描的周期
```

例如：

```c
KEY_MAX_SHOCK_PERIOD = 10; // 10ms
scanner_period = 5;        // 每 5ms 扫描一次

10 / 5 = 2;               // 连续检测 2 次才算有效
```

早期代码调用 `key_init(100)`，计算结果是：

```c
10 / 100 = 0
```

C 语言整数除法会丢弃小数部分，所以结果不是 `0.1`，而是 `0`。随后条件变成：

```c
0 <= key_press_time[i]
```

即使没有按键，`key_press_time[i] == 0`，条件也成立，于是会误报按键。

还要注意：

```c
key_init(10);
```

只会把 `scanner_period` 变量设置为 10，不会自动让程序每 10ms 调用一次扫描函数。实际调用周期必须由 PIT、系统节拍或延时控制。当前主循环使用 `key_init(1)` 和 `system_delay_ms(1)`，比之前更接近，但屏幕刷新等操作也占用时间，因此它仍不是精确的 1ms 周期。

## 5. 为什么光标会一直跑到最后一项

早期错误中，无按键也会被识别为 `KEY_1`。而主程序把 `KEY_1` 映射为光标移动，所以主循环会不断执行移动函数：

```text
s1 -> s2 -> s4 -> s5
```

到达 `s5` 后，因为已经增加了末尾边界检查，光标不会再移动，于是屏幕看起来像是“光标固定在最后一项”。

这不是绘制箭头的函数把光标画错了，而是按键层持续产生了移动事件。

排查这类问题时，应暂时输出每次扫描结果：

```c
printf("key = %d\n", key);
```

如果完全没有按键却不断输出某个有效键值，问题就在按键扫描层，而不是菜单显示层。

## 6. 没有按键时，函数会默认返回 0 吗

不会。下面这种写法是错误的：

```c
key_index_enum key_scanner_re(void)
{
    // 某些分支 return
    // 无按键时直接运行到函数末尾
}
```

非 `void` 函数没有在所有路径明确 `return`，属于未定义行为。ARM 函数通常通过 `R0` 寄存器返回值；没有显式返回时，调用者可能读到寄存器中残留的值。它可能碰巧是 0，也可能是其他值，不能依赖。

当前按键枚举是：

```c
KEY_1 = 0,
KEY_2,
KEY_3,
KEY_4,
KEY_NUMBER,
```

因此可以把 `KEY_NUMBER` 作为“没有按键”的哨兵值：

```c
return KEY_NUMBER;
```

主程序 `switch` 的 `default` 会忽略它。当前源码已经恢复了这个返回值。

## 7. 为什么一次按键可能执行多次

长按分支达到计数后会执行：

```c
key_press_time[i] = 0;
return i;
```

如果按键仍未释放，计数会从 0 重新开始，达到阈值后再次返回相同按键。因此该实现允许长按连发。

如果实际扫描比 `scanner_period` 声明的周期快，一次普通按压也可能在程序看来变成长按，并在短时间内产生多个事件。

菜单中的典型后果是：

```text
第一次 KEY_1：aa -> s5
第二次 KEY_1：s5 -> s4
```

如果只需要“一次按下执行一次”，应使用如下状态过程：

```text
释放态 -> 检测到按下 -> 消抖 -> 确认按下
确认按下 -> 等待释放 -> 产生一次短按事件 -> 释放态
```

产生事件后必须等待释放，不能立刻重新计数。若需要长按连发，也应该单独设置首次长按时间和后续连发间隔。

## 8. 为什么 `aa` 的值只能减、不能加

早期加法代码是：

```c
if(key->sons != 0)
{
    if(F == 1)
    {
        key->data++;
    }
}
```

`aa` 是数据项而不是文件夹，所以它没有子项：

```c
key->sons == 0
```

程序在外层判断就退出了，`key->data++` 永远无法执行。减法没有放在这个条件内，所以表现为“只能减”。

判断顺序应该是：

```c
if(key->kind != Floder)
{
    key->data++;
}
else if(key->sons != 0)
{
    key = key->first_son;
}
```

当前源码的 `enter_meau()` 已经调整了判断顺序。

## 9. 为什么修改菜单值不会修改变量 `a`

当前初始化调用是：

```c
Create_Mem(&s5, &s3, "aa", a, uint16_box);
```

`Create_Mem` 的 `data` 参数按值传递：

```c
void Create_Mem(..., uint32_t data, ...)
{
    me->data = data;
}
```

这相当于：

```text
a 当前的值 -> 复制一份 -> s3.data
```

以后执行 `key->data++`，修改的是 `s3.data`，不是全局变量 `a`。二者已经是两个独立的存储位置。

如果菜单只是保存配置值，保存副本没有问题。如果菜单必须直接修改控制算法中的变量，就应该保存变量地址，并根据 `kind` 转换到对应指针类型后读写。例如概念上应保存 `&a`，而不是 `a`。实现时还必须保证指针指向的变量在菜单整个生命周期内都有效。

## 10. 为什么进入 `aa`、返回后又进不去

菜单初始化中有三个同名节点：

```c
s2: "Meau2"
s4: "Meau2"
s5: "Meau2"
```

但只有 `s5` 拥有子项 `aa`。如果返回键重复触发，光标可能从 `aa` 返回 `s5` 后，又移动到 `s4`：

```text
aa(s3) -> s5 -> s4
```

因为 `s4` 和 `s5` 都显示为 `Meau2`，肉眼会误以为仍选中了原来的节点。但 `s4.sons == 0`，自然无法再次进入 `aa`。

这个问题由两件事共同放大：

1. 按键可能重复产生事件。
2. 多个菜单项使用了完全相同的显示名称。

调试时应暂时使用不同名称，例如 `Meau2-A`、`Meau2-B`、`Meau2-C`，并输出 `key` 地址或 `key->sons`，不要只依赖屏幕文字判断当前节点。

## 11. `F` 为什么容易带来状态问题

当前代码在 `key_show()` 中根据选中项更新 `F`：

```c
if(s->kind != Floder)
{
    F = 1;
}
else
{
    F = 0;
}
```

但 `F` 本质上是 `key->kind` 的重复状态，而且它是在“显示函数”中更新的。菜单动作依赖显示函数提前执行，会让控制逻辑和绘制顺序耦合。一旦调用顺序变化，`F` 可能仍代表上一个节点。

更直接的判断是：

```c
if(key->kind != Floder)
{
    // 当前是数据项
}
```

一般原则：显示函数只负责显示；菜单行为直接读取菜单节点状态，不要让显示函数修改控制状态。

## 12. 无符号数减到 0 以下会发生什么

`Meau_Item.data` 是 `uint32_t`。当它等于 0 时继续执行：

```c
key->data--;
```

不会得到真正的 `-1`，而会发生无符号回绕：

```text
0 -> 4294967295
```

如果显示函数把这组二进制位当作有符号整数解释，屏幕可能显示 `-1`，但变量实际类型仍是 `uint32_t`。

因此修改菜单参数时应设置上下限：

```c
if(key->data < max_value)
{
    key->data++;
}

if(key->data > min_value)
{
    key->data--;
}
```

`uint8_box`、`uint16_box`、`uint32_box` 目前只是标签，结构体中的实际存储统一是 `uint32_t`，代码还没有自动实施对应位宽的范围限制。

## 13. 菜单和摄像头为什么可能互相覆盖

主循环先绘制菜单，随后在摄像头完成一帧时又调用图像显示：

```c
key_show();
data_show();
meau_show();

if(mt9v03x_finish_flag)
{
    ips200_displayimage03x(...);
}
```

如果菜单文字和摄像头图像使用相同屏幕区域，后绘制的内容会覆盖先绘制的内容。此时看到的闪烁、残影或文字消失并不一定是菜单树错误，而可能是两个显示任务争用同一片区域。

解决思路是明确划分显示区域，或者只在界面状态发生变化时切换页面，不要让两个页面每轮同时重绘同一位置。

## 14. 当前代码仍值得改进的地方

以下项目不一定立即导致故障，但会让后续扩展更容易出错：

- `Create_Mem()` 没有显式设置 `me->sons = 0`，现在依赖全局变量自动清零。
- `head.kind` 没有显式初始化为 `Floder`，现在依赖全局变量的零值恰好对应枚举 `Floder`。
- 多个节点都叫 `Meau2`，不利于观察真实选中节点。
- `F` 与 `key->kind` 重复，建议让操作逻辑直接判断 `key->kind`。
- 数据项缺少最小值、最大值和步长，减法可能回绕。
- `Create_Mem()` 保存数值副本，无法直接绑定外部控制变量。
- 文件和标识符中的 `Meau`、`Floder`、`key_dowm` 分别应为 `Menu`、`Folder`、`key_down`。拼写不影响运行，但会增加阅读和搜索成本。

## 15. 推荐的排查顺序

以后再遇到菜单异常，可以按下面顺序检查：

1. 打印 `key`、`key->name`、`key->kind`、`key->sons`，确认选中了哪个真实节点。
2. 不按键时打印扫描结果，确认只返回无按键哨兵值。
3. 按一次键，统计产生了几个事件，排除重复触发。
4. 检查首尾移动是否进行了 `NULL` 判断。
5. 检查显示循环使用的是当前父节点 `h->sons`。
6. 检查进入操作只对文件夹使用 `first_son`，数值操作只对数据项执行。
7. 检查数值的类型、上下限，以及菜单保存的是副本还是变量地址。
8. 检查摄像头、菜单等显示任务是否写入了相同屏幕区域。

最重要的调试原则是：先确认输入事件是否正确，再确认 `key` 的状态变化，最后检查屏幕显示。屏幕只是状态的结果，显示异常不一定表示绘图函数有问题。
